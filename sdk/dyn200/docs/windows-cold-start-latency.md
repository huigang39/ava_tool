# Windows FTDI 冷启动数据批量延迟

2026-09-27，本机 COM11、115200、8N1、protocol 6，FTDI VID 0403 / PID 6001，
VCP 驱动 2.12.36.20。驱动注册表延迟计时器为 16 ms，传输块配置为 4096 字节。
测试未修改驱动注册表，未发送传感器命令。

用户反馈：直接用 ava_tool 连接只有几 Hz，先用串口助手连接再断开则约 700 Hz。
以下对照确认了本机冷启动时存在驱动批量交付延迟，以及事件字符配置能够解决
当前传感器数据下的延迟；没有跟踪串口助手内部调用，不能断言助手具体做了什么。

## 直接读取对照

用户拔插 USB 转接器，未打开串口助手，使用 `example/diagnose_serial.py`：

| 设置 | 有效帧/秒 | 交付批次/秒 | 最大批量 | 最大间隔 |
| --- | ---: | ---: | ---: | ---: |
| 旧 SDK 部分 DCB 初始化 | 919.3 | 4.2 | 3967 B | 661.5 ms |
| 完整 DCB 初始化 | 916.7 | 3.8 | 3967 B | 661.5 ms |
| 完整 DCB + EvtChar=0 + EV_RXFLAG | 1000.2 | 4946.0 | 30 B | 5.0 ms |
| 恢复事件掩码 0 后重新打开 | 916.8 | 3.8 | 3967 B | 661.5 ms |

每组读取 5 秒。低速组仍收到大量有效帧，但间隔数百毫秒才收到一大块；因此
最新值接口和界面无法持续获得新数据。旧 SDK 基准中 `rt_latest` 仅约 22 Hz，
每秒近 50 万次空读并没有改善数据交付。

原始诊断会恢复拔插后的 1200 / 7E1 设置，下一次重新配置期间出现了少量串口
错误和起始错位字节；上述原始诊断不作为“零错误”测试。

## 修复及最终验证

- Windows 完整初始化二进制、无流控 DCB，防止继承接收过滤、门控等旧设置。
- 主动模式 6/8 每次连接和自动重连启用 `EV_RXFLAG`，事件字符为零。
- Modbus 初始化清除事件掩码；后续读取超时调整不改变主动模式事件掩码。
- 事件字符保留在流中，继续按完整帧长度和 CRC 解析。
- 事件配置失败返回配置错误，并由打开流程关闭句柄。

修改后静态 SDK 基准，每个接口运行 5 秒：`rt_latest` 991.8 Hz，`rt_fresh`
1000.1 Hz，`update` 1000.0 Hz，全部零超时、零 CRC 错误。

用户再次拔插后，直接通过 Python ctypes 加载最终 `lib/win/dyn200.dll`，调用
`dyn200_open_active` 和 `dyn200_update`，连续三次打开/读取 5 秒/关闭：

| 连接 | 新帧/秒 | 错误数 | 最长读取 |
| --- | ---: | ---: | ---: |
| 首次冷启动 | 1000.4 | 0 | 2.155 ms |
| 再次连接 | 1001.0 | 0 | 1.910 ms |
| 第三次连接 | 1001.1 | 0 | 1.933 ms |

`make all test` 通过；新增回归覆盖污染 DCB、事件配置失败、重试、读取超时更新
不关闭事件交付。协议 8 未连接实物测试；界面刷新频率仍受采集周期和显示周期限制。

## 适用范围

FTDI 事件字符只能在匹配字节出现时促进交付。零字节不是协议必有分隔符，
若数据长期不含零字节，仍可能受驱动缓冲策略影响。本次实测不代表所有力矩、
转速数据及所有转接器都有固定的 1000 Hz 上限或保证。

参考：[FTDI Win32 示例 AN232-06](https://www.ftdichip.cn/Support/Documents/AppNotes/AN232-06.pdf)、
[FTDI 事件字符说明](https://ftdichip.com/Support/Knowledgebase/an232b_04eventchar.htm)。
